# SPEC.md

# DeepStream Car Tracking

**Версия:** 0.1  
**Статус:** техническое задание V1

---

## 1. Назначение

Нужно создать локальную систему видеоаналитики для нескольких IP-камер.

Система должна:

- получать HLS/RTSP видеопотоки;
- декодировать видео аппаратно на NVIDIA GPU;
- выполнять детекцию автомобилей;
- отслеживать автомобили внутри каждого потока;
- формировать структурированные события и метаданные;
- при необходимости сохранять кадры, связанные с событием;
- устойчиво работать при временной недоступности отдельных камер.

Основной runtime — NVIDIA DeepStream на Ubuntu.

## 4. Основная архитектура

Целевой pipeline:

```text
HLS / RTSP
    ↓
GStreamer source
    ↓
NVIDIA hardware decode / NVDEC
    ↓
GPU resize / conversion
    ↓
nvstreammux
    ↓
nvinfer
    ↓
YOLOv8 TensorRT
    ↓
nvtracker
    ↓
event logic
    ↓
metadata / logs / optional JPEG evidence
```

Основные принципы:

1. Основной video runtime — DeepStream.
2. Видео не должно постоянно копироваться CPU ↔ GPU без необходимости.
3. Декодирование выполняется аппаратно.
4. Несколько источников объединяются через `nvstreammux`.
5. Inference выполняется TensorRT через `nvinfer`.
6. Tracking выполняется после detector.
7. Масштабирование выполняется на GPU.
8. Обрабатывается полный кадр.
9. Производительность регулируется batching, resolution и inference interval.
10. V1 использует локальный tracking по каждой камере.

---

## 5. Модель

На первом этапе используется стандартный YOLOv8, обученный на COCO.

Первый целевой класс:

`car`

Не требуется сохранять совместимость со старой кастомной моделью.

Production inference:

```text
YOLOv8 .pt
    ↓
ONNX
    ↓
TensorRT engine
    ↓
DeepStream nvinfer
```

Формат интеграции должен соответствовать DeepStream 7.0 и фактически используемой версии TensorRT.

Если YOLOv8 требует custom parser/plugin, использовать минимально необходимую реализацию и не создавать собственный inference framework поверх DeepStream.

---

## 6. Обработка кадра

Старый прототип делил изображение на левую/правую части и обрабатывал crop.

В новой версии это не используется.

Требование V1:

- анализировать полный кадр;
- допустимо уменьшать разрешение перед inference;
- resize должен выполняться средствами GPU/DeepStream;
- конкретное рабочее разрешение определяется benchmark, а не старым prototype.

Начальная гипотеза:

- входной кадр: исходное разрешение камеры;
- рабочий pipeline: около 1280×720;
- вход YOLO: около 640×640.

Это стартовая конфигурация для измерений, а не жёсткий архитектурный контракт.

---

## 7. Источники видео

Первая версия должна поддерживать HLS и/или RTSP через GStreamer/DeepStream.

Часть текущих HLS источников требует HTTP headers, например:

- `Referer`;
- `User-Agent`.

Конфигурация источников должна храниться вне основного кода.

Нельзя хранить credentials в Git.

Система должна корректно переживать:

- недоступную камеру при старте;
- временный обрыв потока;
- восстановление потока;
- потерю одной камеры без падения остальных потоков.

Старый файл `scaner_5cam_nebo.py` может использоваться только как источник информации о:

- URL/типе потоков;
- required headers;
- реальном поведении камер при ошибках.

Нельзя переносить из старого prototype как архитектуру:

- запуск отдельного `ffmpeg` на каждый кадр;
- split/crop логику;
- сериализацию inference через `model_lock`;
- старый threading model;
- старую логику сохранения кадров без отдельного решения.

---

## 8. Tracking

V1 использует `nvtracker`.

Требование:

- track ID существует только в рамках одной камеры;
- один и тот же автомобиль на разных камерах не обязан иметь одинаковый ID;
- tracker должен продолжать сопровождение между detector frames, когда используется inference interval.

Выбор конкретного tracker backend (`NvDCF`, `NvSORT` и т.п.) должен делаться на основании benchmark и качества, без изменения общей архитектуры.

---

## 9. События и данные

После detector/tracker pipeline должен быть слой event logic.

Минимальные данные объекта:

- source/camera id;
- timestamp;
- class id/name;
- confidence;
- bounding box;
- track id, если доступен.

Формат события должен быть простым и сериализуемым.

JPEG evidence допускается сохранять только по событию/правилу, а не обязательно для каждого обработанного кадра.

База данных в V1 не требуется.

---

## 10. Конфигурация

Не хардкодить в Python/C++:

- URLs камер;
- credentials;
- HTTP headers;
- пути к model/engine;
- thresholds;
- inference interval;
- рабочее resolution;
- tracker config;
- директории output.

В репозитории должны храниться только безопасные конфиги и templates.

---

## 11. Производительность

Целевая машина: RTX 3060 12 GB.

Начальная цель V1 для 5 источников:

- ориентир: не менее 10 обработанных FPS на источник;
- end-to-end latency ориентировочно до 2 секунд;
- длительная работа без накопления GPU/CPU memory leak.

Это performance targets, которые нужно измерять на реальных потоках. Они не должны достигаться искусственным усложнением архитектуры до появления benchmark.

Система должна позволять снижать нагрузку через:

1. уменьшение processing resolution;
2. увеличение inference interval;
3. tracker между detector frames;
4. batching;
5. отключение ненужного display/encoding.

---

## 12. Надёжность

Одна проблемная камера не должна завершать весь процесс.

Нужны:

- понятные ошибки источника;
- reconnect/retry;
- логирование состояния источников;
- корректное завершение pipeline;
- отсутствие бесконечного роста памяти;
- отсутствие silently swallowed fatal errors.

Целевой дальнейший benchmark — длительный runtime до 7 суток, но сначала должны быть доказаны короткие стабильные прогоны.

---

## 13. Простота реализации

Проект должен оставаться максимально простым.

Предпочтительно:

- небольшой набор модулей;
- функции вместо классов, если lifecycle/state не требуют класса;
- минимальное количество зависимостей;
- DeepStream/GStreamer возможности вместо самописных аналогов;
- конфиги вместо хардкода;
- никакой инфраструктуры «на будущее».

## 14. Этапы реализации

### Этап 0 — environment baseline

Цель:

- воспроизводимо проверить текущий runtime;
- не менять систему.

Проверяются:

- NVIDIA GPU/driver;
- CUDA;
- TensorRT;
- cuDNN;
- DeepStream;
- GStreamer;
- `nvinfer`;
- `nvstreammux`;
- `nvtracker`.

Среда уже вручную проверена, включая успешный `deepstream-app` sample. В проекте при необходимости может появиться read-only диагностический script.

### Этап 1 — минимальный DeepStream pipeline

Цель:

- один контролируемый источник;
- аппаратный decode;
- `nvstreammux`;
- рабочий pipeline;
- без сложной бизнес-логики.

Acceptance:

- pipeline запускается;
- источник читается;
- корректно завершается;
- ошибки понятны.

### Этап 2 — YOLOv8 + TensorRT + nvinfer

Цель:

- интегрировать YOLOv8 COCO;
- получать detector metadata;
- оставить только нужные классы, начиная с `car`.

Acceptance:

- detector работает на Ubuntu GPU;
- TensorRT engine строится/загружается;
- `car` detections доступны в metadata.

### Этап 3 — tracker

Цель:

- добавить `nvtracker`;
- получить стабильные local track IDs.

### Этап 4 — реальные HLS/RTSP камеры

Цель:

- подключить реальные источники;
- headers;
- reconnect;
- поведение при недоступной камере.

### Этап 5 — multi-camera

Цель:

- 5 источников;
- batching;
- нагрузочные измерения;
- подбор resolution / interval / tracker.

### Этап 6 — event layer

Цель:

- структурированные события;
- логи;
- optional JPEG evidence.

### Этап 7 — stability/performance

Цель:

- длительные прогоны;
- memory/GPU monitoring;
- recovery tests;
- performance benchmark.

Не переходить к следующему этапу, пока текущий не проверен.

## 16. Критерии приёмки V1

V1 считается функционально готовой, когда:

1. Проект запускается на целевой Ubuntu машине.
2. Использует DeepStream 7.0 и NVIDIA GPU.
3. Работает минимум с 5 потоками.
4. Выполняет hardware decode.
5. Выполняет YOLOv8 TensorRT inference через `nvinfer`.
6. Детектирует `car`.
7. Работает по полному кадру.
8. Выполняет local tracking через `nvtracker`.
9. Отказ одной камеры не завершает остальные потоки.
10. Источник может восстановиться после временного обрыва.
11. Параметры pipeline задаются конфигурацией.
12. Секреты не хранятся в Git.
13. Формируются понятные detection/tracking metadata.
14. Производительность измерена на RTX 3060.
15. Нет известных критических memory/resource leaks на проверенном интервале работы.

## 17. Итоговый принцип

Система должна быть:

- простой;
- локальной;
- GPU-ускоренной;
- устойчивой;
- понятной;
- расширяемой без преждевременного усложнения.

Главная задача V1:

**надёжно обрабатывать несколько IP-камер через NVIDIA DeepStream, детектировать автомобили YOLOv8/TensorRT и отслеживать их внутри каждого видеопотока.**
