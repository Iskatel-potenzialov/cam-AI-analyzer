# Многокамерная cистема видеоаналитики

Многокамерная система видеоаналитики на DeepStream.

Система получает несколько HLS-потоков с камер, обрабатывает видео на GPU, запускает YOLOv8 через TensorRT, отслеживает объекты между кадрами и превращает результаты компьютерного зрения в понятные прикладные данные: события, счётчики, текущее состояние зон и данные для веб-интерфейса.
Для демонстрации используются публично доступные городские камеры сервиса «Интерра Онлайн» (https://online.interra.ru/)

Сейчас реализованы два сценария:

- **Case 1 — транспорт:** автомобили, мотоциклы и автобусы, пересечение виртуальных линий и счётчики по направлениям.
- **Case 2 — люди в зонах:** RED / YELLOW / GREEN зоны, текущее количество людей в каждой зоне и события входа в RED.

Основной видеоконвейер построен по GPU-first (приоритет обработки на GPU) принципу: декодирование, подготовка кадров, TensorRT-inference и отрисовка выполняются средствами NVIDIA DeepStream/GStreamer, а кадры по возможности остаются в GPU/NVMM-памяти без постоянного копирования в OpenCV/Python.

| Сценарий | Что анализируется | Что получает пользователь |

| **Case 2 — зоны** | `person` | число людей в RED/YELLOW/GREEN, ID ) объектов, входы в RED, история событий, актуальный кадр |

## Подготовка датасета и дообучение модели

В систему добавлен собственный модуль сбора данных для последующего дообучения YOLO. Он автоматически сохраняет чистые кадры из ROI камеры вместе с предразметкой текущей модели в формате Ultralytics YOLO.

Отбор данных выполняется не только с фиксированным интервалом, но и по сложным ситуациям: близко расположенные люди, пересекающиеся bounding box, подозрительно широкие детекции, резкие изменения bbox и другие потенциальные ошибки детекции и трекинга.

Собранный датасет можно вручную скорректировать в CVAT/Roboflow и использовать для fine-tuning YOLOv8, после чего обученная модель возвращается в DeepStream через ONNX → TensorRT. Такой цикл позволяет постепенно улучшать качество модели именно на реальных сценах целевой камеры.

## Архитектура

```text

        │
        ▼

        │
        ▼

        │
        ▼

        │

        │
        ▼

        │
        ├─────────────────────────────┐
        │                             │
        ▼                             ▼
Логика сценария                 ветка актуального кадраes
линии / зоны / правила         отдельный OSD (графическая разметка поверх видео) → JPEG
        │                             │
        ├──────────────┐              ▼

        │              │              ▼
        ▼              ▼            React

        │

```

Отдельно работает локальный операторский экран DeepStream:

```text
nvtracker (модуль отслеживания)
  → nvmultistreamtiler
  → nvvideoconvert
  → nvdsosd
  → nveglglessink
```

То есть локальный экран, backend (серверная часть) и веб-интерфейс не зависят друг от друга жёстко. Каждый слой решает свою задачу.

## Как проходит видео через систему

1. Камеры передают HLS/RTSP-видео.
2. `nvv4l2decoder` аппаратно декодирует его через NVIDIA NVDEC.
3. `nvstreammux` объединяет несколько камер в один batch (пакет кадров).
4. `nvdspreprocess` подготавливает входные изображения для нейросети.
5. `nvinfer` запускает YOLOv8 через TensorRT на GPU.
6. Перед tracker (модуль отслеживания) оставляются только нужные классы:
   - `видеопоток0` — `car`;
   - `видеопоток1` — `person`;
   - `видеопоток)–4` — object metadata (служебные данные об объектах) удаляется, но само видео продолжает идти дальше.
7. NvDCF присваивает объектам `tracker_id`, чтобы понимать, что объект на соседних кадрах — это всё тот же человек или автомобиль.
8. C++-логика определяет пересечения линий или принадлежность зонам.
9. Результат идёт сразу в несколько направлений:
   - на локальный экран;
   - в backend;
   - в API актуального кадра;
   - во frontend.

##  DeepStreamV

Основной видеопуть построен на NVIDIA DeepStream:

- **NVDEC** — аппаратно декодирует видео;
- **NVMM** — позволяет передавать кадры между NVIDIA-компонентами без обычного копирования в OpenCV;
- **`nvstreammux`** — объединяет несколько камер;
- **`nvdspreprocess`** — готовит кадры для модели;
- **`nvinfer`** — запускает TensorRT inference;
- **`nvtracker (модуль отслеживания)` / NvDCF** — отслеживает объекты;
- **`nvmultistreamtiler`** — собирает камеры в общий экран;
- **`nvdsosd`** — рисует bbox, линии, зоны и текст.


### batching (пакетная обработка)

Сейчас основной pipeline (конвейер обработки) работает с пятью источниками и статическим batch-5 TensorRT engine.

Это значит, что несколько камер перед inference объединяются в один пакет.

Вместо того чтобы запускать отдельную модель для каждой камеры, один GPU-конвейер обрабатывает сразу несколько источников.

# Case 1 — транспортная аналитика

## Что делает

На `видеопоток 0` система анализирует:

- автомобили (`car`);


YOLOv8 находит объект и определяет его класс.

NvDCF отслеживает этот объект на следующих кадрах и сохраняет его `tracker (модуль отслеживания)_id`.

После этого система уже работает не с отдельными кадрами, а с движением конкретного объекта во времени.

---

## ROI (область интереса) и виртуальные линии

Аналитика работает внутри заданной области — ROI (область интереса).

Внутри неё заданы три виртуальные линии:

- **RED** — считает движение снизу вверх;
- **GREEN** — отдельно считает движение слева направо и справа налево;
- **BLUE** — считает движение справа налево.

В результате получаются четыре независимых счётчика:

1. RED: bottom → top;
2. GREEN: left → right;
3. GREEN: right → left;
4. BLUE: right → left.

Для определения положения автомобиля используется нижняя центральная точка bbox (`bottom-center`).

Для дорожной сцены это удобнее, чем центр bbox, потому что эта точка ближе к месту, где объект соприкасается с дорогой.

---

## Как система понимает, что линия действительно пересечена

Нельзя просто считать объект каждый раз, когда он оказался по другую сторону линии.

BBox немного двигается от кадра к кадру. Если не учитывать это, один автомобиль можно случайно посчитать несколько раз.

Поэтому логика проверяет:

- где объект был на предыдущем кадре;
- где он находится сейчас;
- в каком направлении он движется;
- пересёк ли он именно конечный отрезок линии;
- находится ли он в допустимой зоне около линии;
- считался ли уже этот `tracker_id` для этой линии.

Так счётчик опирается на реальное движение объекта между кадрами, а не на один случайный кадр.

---

## Что видит оператор

Для Case 1 на кадре отображаются:

- ROI (область интереса);
- RED / GREEN / BLUE линии;
- четыре счётчика;
- bbox  транспорта;
- confidence (уверенность модели);
- `tracker_id`.

Пример подписи:

```text
0.87 ID:42
```

После подтверждённого пересечения создаётся persistent событие (сохраняемое событие), который отправляется в FastAPI и сохраняется в PostgreSQL.

# Case 2 — контроль людей в зонах

## Что делает

На `видеопоток 1` система анализирует только людей (`person`).

Внутри общего ROI (область интереса) заданы зоны:

- **RED** — критическая;
- **YELLOW** — предупреждающая;
- **GREEN** — безопасная.

Для определения положения человека также используется нижняя центральная точка bbox.

---

## Приоритет зон

Если человек одновременно попадает под несколько геометрических правил, используется такой приоритет:

```text
RED > YELLOW > GREEN > OUTSIDE
```

То есть система всегда выбирает наиболее критичный статус.

---

## Зона подтверждается двумя кадрами

BBox tracker может немного двигаться между кадрами.

Особенно это заметно, если человек стоит около границы двух зон.

Без дополнительной проверки состояние может выглядеть так:

```text
GREEN → YELLOW → GREEN → YELLOW
```

хотя человек почти не двигался.

Поэтому новая зона считается подтверждённой только после двух последовательных кадров.

Это делает состояние стабильнее.

---

## Ссохраняемое событие и текущее состояние

Case 2 разделяет две разные вещи:

- **историческое событие**;
- **текущее состояние камеры**.

### Persistent событие (сохраняемое событие)

Когда человек подтверждённо входит в RED, создаётся событие:

```text
событие_type = red_zone_entry
rule_id    = case2_red
camera_id  = видеопоток 1
```

Оно отправляется в FastAPI и сохраняется в PostgreSQL.

Это факт, который нужен в истории.

### Live state (текущее состояние)

Отдельно DeepStream примерно раз в секунду отправляет текущее состояние камеры:

- сколько людей в RED;
- сколько в YELLOW;
- сколько в GREEN;
- `tracker_id`;
- confirmed zone;
- confidence.

Live state хранится только в RAM backend.

**Почему отдельно:** вход в RED — это событие, которое важно сохранить. Текущее количество людей в зоне постоянно меняется, поэтому записывать его в PostgreSQL каждую секунду нет смысла.

# Snapshot (актуальный кадр) для веб-интерфейса

Frontend показывает актуальный JPEG для Case 1 и Case 2.

Это не скриншот окна DeepStream и не второй запуск YOLO.

Snapshot (актуальный кадр) создаётся внутри того же GStreamer pipeline (конвейер обработки):

```text
nvtracker (модуль отслеживания)
  → tee
      ├─ основной экран
      │    → tiler → OSD (графическая разметка поверх видео) → monitor (мониторинг ресурсов)
      │
      └─ snapshot (актуальный кадр)
           → nvstreamdemux
           → RGBA/NVMM
           → свой OSD (графическая разметка поверх видео)
           → ROI (область интереса) crop
           → nvjpegenc
           → latest JPEG
```

JPEG обновляется примерно раз в секунду.

---

## Актуальный кадр использует свой OSD (графическая разметка поверх видео)

Перед разделением веток система сохраняет небольшой cache состояния по PTS кадра.

В нём хранятся обычные C++-данные:

- номер кадра;
- счётчики;
- bbox;
- `tracker (модуль отслеживания)_id`;
- confidence ;
- confirmed zone.

После `nvstreamdemux` ветка актуального кадра:

1. берёт metadata (служебные данные об объектах) своего кадра;
2. удаляет старые экран/object metadata;
3. находит состояние этого же кадра по PTS;
4. создаёт новый `NvDsЭкранMeta`;
5. заново рисует нужный Case 1 или Case 2 overlay (графическая разметка поверх кадра);
6. кодирует результат в JPEG.

# Асинхронная отправка событий

DeepStream не делает HTTP-запрос прямо внутри обработки кадра.

Вместо этого:

```text
CV analytics
    ↓
очередь событий
    ↓
отдельный libcurl фоновый поток
    ↓
FastAPI
```

Очередь ограничена 100 событиями.

Для сетевых ошибок и HTTP `5xx` выполняется до двух повторных попыток с тем же `событие_id`.

HTTP `4xx` повторно не отправляются.

Если backend отвечает медленно или сеть временно недоступна, video pipeline (конвейер обработки) не должен останавливаться.

Камеры, inference и tracking продолжают работать независимо от скорости HTTP API.

---

## run_id

Каждый запуск DeepStream получает новый UUID (идентификатор) `run_id`.

Он добавляется к событиям.

Это позволяет отличать события разных запусков системы и удобно сверять runtime (работа системы)-счётчики с данными в PostgreSQL.

# Backend (серверная часть)

Backend написан на FastAPI.

Он отвечает за:

- приём persistent CV событиеs;
- хранение истории в PostgreSQL;
- приём и выдачу Case 2 live state (текущее состояние);
- выдачу последних JPEG snapshot (актуальный кадр).

Основные endpoints:

```text
POST /api/v1/событиеs
POST /api/v1/live-state
GET  /api/v1/live-state/{camera_id}

GET  /api/v1/cameras/source0/snapshot.jpg
GET  /api/v1/cameras/source1/snapshot.jpg
```

Если DeepStream ещё не успел сформировать первый snapshot (актуальный кадр), endpoint возвращает `404`.

## Отдельные модели для разных задач

Текущий общий YOLOv8 удобен для разработки и проверки архитектуры.

Дальше камеры можно группировать по задачам:

```text
helmet cameras
  → own nvstreammux
```

# Ключевая идея проекта

Проект не сводится к запуску YOLO на видеопотоке.

Цель — построить основу многокамерной CV-системы, где каждый слой отвечает за свою задачу:

```text
camera input
→ GPU inference (запуск нейросети)
→ tracking (отслеживание объектов)
→ business правила
→ событиеs / live state (текущее состояние)
→ backend (серверная часть)
→ operator UI
```

Модель отвечает за распознавание объекта.

Tracker (модуль отслеживания) — за то, чтобы понимать, что это тот же объект на следующем кадре.

Прикладная логика — за смысл события.

Backend (серверная часть) — за историю и текущее состояние.

Frontend (веб-интерфейс) — за отображение результата оператору.

Так можно добавлять новые камеры, новые модели и новые прикладные сценарии без необходимости строить отдельный монолитный CV-скрипт для каждой новой задачи.
