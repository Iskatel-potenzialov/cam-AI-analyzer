# AGENTS.md

## Назначение

Этот файл содержит обязательные правила работы Codex с проектом **DeepStream Car Tracking**.

Перед любыми изменениями Codex должен прочитать:

1. `AGENTS.md`
2. `SPEC.md`
3. `README.md`

`SPEC.md` — источник требований и архитектурных ограничений.  
`README.md` — краткое описание проекта и рабочей среды.  
Правила из `AGENTS.md` обязательны всегда.

---

## 1. Главный принцип

**Не усложнять.**

Реализовывать только то, что требуется текущей задачей и `SPEC.md`.

Запрещено без необходимости:

- добавлять архитектурные слои и абстракции;
- создавать функциональность «на будущее»;
- добавлять новые библиотеки и сервисы;
- переписывать работающий код ради «красоты»;
- менять выбранный стек на альтернативный.

Предпочтение отдаётся:

- простому коду;
- небольшим модулям;
- обычным функциям, если класс не нужен;
- минимальному количеству файлов;
- уже существующим зависимостям;
- минимальному diff.

---

## 2. Работа только в границах проекта

Codex работает с каталогом проекта:

`/home/evgeny/CV/deepstream-car-tracking`

На Windows этот каталог смонтирован как диск `Z:`.

Codex не должен:

- изменять файлы за пределами проекта;
- выполнять `sudo`;
- изменять NVIDIA Driver, CUDA, cuDNN, TensorRT, DeepStream или системный GStreamer;
- устанавливать или удалять системные пакеты;
- изменять другие conda/venv окружения;
- останавливать чужие процессы и приложения;
- менять конфигурацию Ubuntu без отдельного разрешения.

Если для задачи требуется системное изменение — остановиться и сообщить пользователю точную команду и причину.

---

## 3. Граница среды выполнения

Codex работает локально в VS Code на Windows и редактирует файлы Ubuntu через SSHFS-диск `Z:`.

Поэтому Codex не должен считать Windows-терминал Ubuntu-runtime.

Реальные проверки, требующие Ubuntu/GPU, выполняются вручную пользователем на Ubuntu, в частности:

- `deepstream-app`;
- DeepStream GStreamer plugins;
- CUDA;
- TensorRT;
- cuDNN;
- NVIDIA GPU;
- `CV-venv`;
- реальные HLS/RTSP потоки;
- TensorRT engine build;
- GPU performance tests.

Codex может запускать только те проверки, которые действительно доступны в его текущей среде.

**Нельзя заявлять, что проверка пройдена, если она фактически не запускалась.**

Если проверку нельзя выполнить локально, Codex должен:

1. явно указать это;
2. дать точную команду для Ubuntu;
3. описать ожидаемый результат.

---

## 4. Архитектура

Архитектура определена в `SPEC.md`.

Без отдельного согласования нельзя:

- заменять DeepStream другим video runtime;
- убирать `nvstreammux`, `nvinfer` или `nvtracker` из V1;
- переносить основной runtime на Windows;
- возвращать старую схему crop/split кадров;
- добавлять cross-camera ReID/MTMC;
- добавлять базы данных, Redis, Celery, Kafka, Kubernetes и другие инфраструктурные компоненты;
- добавлять Docker только ради упаковки проекта;
- менять публичные конфиги/контракты без необходимости.

Если Codex считает, что архитектуру нужно изменить:

1. не вносить изменение;
2. описать проблему;
3. объяснить, почему текущая архитектура мешает;
4. предложить минимальное изменение;
5. перечислить затрагиваемые файлы;
6. дождаться подтверждения пользователя.

---

## 5. Минимальные изменения

При каждой задаче:

- менять только необходимые файлы;
- не делать попутный рефакторинг;
- не форматировать целиком файл ради небольшого изменения;
- не переименовывать сущности без необходимости;
- не перемещать файлы без необходимости;
- не менять соседние модули, если текущая задача этого не требует;
- сначала переиспользовать существующий код, потом создавать новый.

Перед изменением нескольких файлов Codex должен понимать, зачем нужен каждый из них.

---

## 6. Зависимости

Добавлять только действительно необходимые зависимости.

Перед новой зависимостью проверить:

1. можно ли решить задачу стандартными средствами;
2. есть ли уже подходящая зависимость;
3. действительно ли новая зависимость упрощает решение.

Не добавлять dependency «на будущее».

Системные зависимости Codex не устанавливает.

Python-зависимости проекта должны быть совместимы с отдельным Ubuntu venv:

`/home/evgeny/CV/CV-venv`

---

## 7. Работа по этапам

Не реализовывать весь проект одним проходом.

Для каждой задачи:

1. прочитать текущую задачу и релевантные части `SPEC.md`;
2. изучить существующий код;
3. определить минимальный набор файлов;
4. реализовать только текущую задачу;
5. выполнить доступные проверки;
6. сделать self-review;
7. выполнить `git diff --check`, если Git уже инициализирован и команда доступна;
8. сообщить:
   - какие файлы созданы;
   - какие файлы изменены;
   - что реализовано;
   - какие проверки реально выполнены;
   - какие проверки нужно вручную выполнить на Ubuntu;
   - какие проблемы остались;
9. остановиться и не переходить к следующему этапу без команды пользователя.

---

## 8. Ошибки и спорные требования

Если требование:

- технически невозможно;
- несовместимо с установленным стеком;
- противоречит другому обязательному требованию;
- требует существенного архитектурного изменения;

Codex не должен молча менять решение.

Нужно описать проблему и предложить минимальный вариант исправления.

---

## 9. Git

Codex не должен без отдельной команды пользователя:

- делать `git commit`;
- делать `git push`;
- менять удалённые репозитории;
- переписывать историю;
- удалять ветки.

Разрешены read-only Git-команды и проверка diff, если они доступны.

---

## 10. Секреты

Не хранить в репозитории:

- логины и пароли камер;
- токены;
- API keys;
- приватные URL с credentials;
- другие секреты.

Для секретов использовать локальные конфиги или переменные окружения, а в репозитории хранить только шаблоны.

---

## 11. Definition of Done

Задача завершена, если:

- реализовано только требуемое;
- архитектура не изменена без согласования;
- затронут минимальный набор файлов;
- не добавлены лишние зависимости;
- выполнены все доступные проверки;
- отдельно перечислены проверки, которые требуют Ubuntu/GPU;
- README обновлён, если изменились запуск, зависимости или workflow;
- Codex дал краткий отчёт и остановился.
